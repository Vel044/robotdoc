## 三、逐组解读

### B 组：strace —— 扰动量级与 baseline 不同档

`strace -f -ttT` 通过 `ptrace` 拦截每个系统调用，把每次 syscall 拆成"进入 → 用户态拦截 → 出返"三段，结果是：

- `voluntary_cs` 约为 baseline 的 **31 倍**，`involuntary_cs` 约 **7 倍**：每个 syscall 都被强制切换到 strace 写日志的流程；
- `system_time_s` ≈ 2 倍：内核态多了大量 ptrace stop/resume 工作；
- `obs_pct` 从 13.7 % 飙到 48.5 %（+34.8 pp）：摄像头链路里 `pselect6` / `read` / `ioctl` 数量极大，受 strace 拦截最严重；
- `wait_pct` 从 36.6 % 掉到 5.0 %（−31.6 pp）：不是 wait 真的变少，而是 episode 总时长被 strace 系统性拉长，剩余等待空间被挤压。

**结论**：strace 不能做正式的阶段时间数据来源。在 2.5 节里把它定位为"前期定性看 syscall 类型分布"的工具，这次实验提供了最直接的扰动证据。

### C 组：ftrace 延迟导出 —— 与 baseline 最接近

C 组只在 episode 期间向内核 ring buffer 写事件，没有任何用户态读盘进程参与：

- `system_time_s` 1.37 ≈ baseline 1.40，`voluntary_cs` 30 k 仅比 baseline 高 27 %；
- `wait_pct` 漂移仅 −0.9 pp，符合验收的 ±3 pp 阈值；
- `obs_pct` 漂移 −5.5 pp 略超 ±3 pp 阈值；这一项与"baseline 单次的 obs_s 偏高（4.10 s vs C 的 2.44 s）"高度相关，而不是 ftrace 让 obs 变快了。在 n=1 的样本下属于摄像头首次抓帧抖动，不能定性归因于 ftrace；
- `fps_mean` 下降 13.9 %，仍超过设计文档里 ≤ 5 % 的验收线，但这同样受 obs 单次抖动影响；
- trace 文件 168 MB，逼近 4 核 × 32 MB 的 ring buffer 容量；本组未单独检查 lost events，正式实验时需 `grep -c "lost" raw/ftrace_C_*.txt` 确认是否需要进一步调大 buffer 或缩短 episode。

**结论**：ftrace 延迟导出是目前最接近 baseline 的方案，**推荐作为论文正式实验的内核态时间来源**。

### D 组：ftrace 实时导出 —— 主要开销在用户态导出链路

D 组在 record 之前启动后台 `cat /sys/kernel/debug/tracing/trace_pipe > raw/ftrace_D_*.txt`：

- 与 C 组对比，唯一新增的成本是用户态读 `trace_pipe` + 写日志；
- `voluntary_cs` 和 `involuntary_cs` 与 C 组相近，没有出现 strace 那种几何级放大；
- `fps_mean` 12.48 比 C 的 13.89 略低，差距约 9 %；
- trace 文件 **823 MB**，是 C 组的 4.9 倍——这是因为 D 组没有 ring buffer 容量上限，整个 episode 期间所有事件都被持续导出。

**结论**：D 组本身不致命，但"额外的 5× 数据量、外加 9 % 左右的 FPS 损失"对于本论文这种"事件量并不算极端、episode 仅 30 s"的工作负载是不划算的；用 D 组的唯一理由是 ring buffer 会溢出。本次 C 组没有溢出迹象，所以 D 组没有必要在正式实验里出现。

## 四、对照设计文档的验收标准

设计文档第 8 节给出的硬性指标：

| 指标 | 阈值 | A | B | C | D |
|---|---|---|---|---|---|
| FPS 下降 | ≤ 5 % | — | ❌ −40.9 % | ❌ −13.9 % | ❌ −22.6 % |
| 任一阶段占比漂移 | ≤ ±3 pp | — | ❌ obs +34.8 | ⚠ obs −5.5 | ✅ |
| `system_time_s` 不接近 strace 量级 | — | — | ❌ ×2 | ✅ ×0.98 | ✅ ×0.74 |
| trace 无 lost events | — | — | n/a | ⚠ 未验 | ⚠ 未验 |
| 温度/频率无降频 | — | ✅ 50.7→58.4 °C @2400 MHz | ✅ 49.6→58.4 @2400 | ✅ 51.2→61.1 @2400 | ✅ 48.0→59.5 @2400 |

C/D 两组的 FPS 都没达到 ≤ 5 % 的硬性阈值，主要原因是 n=1 样本下 baseline 自己也带波动（A 组 obs_s 单次偏高就足以拉开 2 fps 差距）。**结论是不能凭这份数据宣布"ftrace 对正式实验无干扰"**；但 B / C / D 之间的相对秩序非常稳定，足以支撑工具选型决策。

## 五、论文第 2.5 节可写回的实测结论

> 在固定 `chunk_size = 100`、目标 `fps = 30`、episode ≈ 30 s 的同一条 record_loop 上，对比 baseline、`strace -f -ttT`、ftrace 延迟导出、ftrace 实时导出四组：`strace` 组系统时间约为 baseline 的 2 倍，自愿上下文切换增至约 31 倍，FPS 下降 40 % 以上，因此仅适合用于系统调用分布的定性确认；ftrace 延迟导出组在系统时间和上下文切换上与 baseline 持平，是单 episode 扰动最小的方案，被采用为本文正式实验的内核态时间来源；ftrace 实时导出组带来约 5 倍的 trace 数据量但额外开销主要集中在用户态 I/O 上，仅在 ring buffer 即将溢出时才作为后备方案使用。
