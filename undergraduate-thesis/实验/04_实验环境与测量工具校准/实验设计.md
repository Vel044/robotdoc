# 实验设计：实验环境与测量工具校准

## 1. 实验定位

这个实验服务第 2 章，不服务第 4 章优化。它要补的是“实验方法可信度”：同一条 `record_loop` 路径，在不开 tracing、开 `strace`、开 `ftrace`、实时导出 trace、使用 `trace-cmd` 时，主循环会不会被测量工具明显扰动。

第 2 章里可以把它放在 2.5 工具链选型之后，作为 `strace` 和 `ftrace` 取舍的实测依据；2.6 的硬件软件配置则由本实验的环境快照固化。

## 2. 固定条件

| 项目 | 固定值 |
|---|---|
| 推理主机 | 树莓派5，ARM Cortex-A76，4 核，4 GB LPDDR4X，无 GPU |
| 系统 | Raspberry Pi OS |
| 机器人 | SO-101，在线推理使用 1 个 follower，6 个舵机 |
| 摄像头 | 2 路 OpenCV USB 摄像头，640 x 360，30 fps |
| record 参数 | `chunk_size=100`，目标 `fps=30`，episode 约 30 s |
| 任务 | 固定一个代表任务，建议使用抓取任务 |
| 重复次数 | 预实验每组 3 次；正式实验每组 5 次 |
| 环境 | 同一供电、同一 USB 连接、同一模型权重、同一 camera index |

正式实验前先空跑 1 个 episode，排除冷启动、模型首次加载和摄像头首次初始化的影响。后续每组之间间隔 30--60 s，让树莓派温度回到接近状态。

## 3. 实验分组

### A 组：baseline

不开任何 tracing。只保留 LeRobot 自身阶段计时日志，并用 `/usr/bin/time -v` 包住 record 命令。

这组回答：在最接近真实运行的条件下，FPS、阶段占比、CPU 时间和内存占用是多少。

### B 组：strace

用 `strace -f -ttT -o raw/strace_RUN.log` 包住完全相同的 record 命令。

这组不追求“准确性能”，而是故意量化 `strace` 的扰动。重点看 `system_time_s`、上下文切换次数和 FPS 是否明显变坏。只要这组明显偏离 baseline，就能支撑论文里的判断：`strace` 适合前期定性探索，不适合最终定量计时。

### C 组：ftrace 延迟导出

episode 开始前同样要打开所需 tracepoint，并把 `tracing_on` 置为 1。区别是 episode 运行期间不启动任何用户态读日志进程，只让事件写入内核 ring buffer；episode 结束后先把 `tracing_on` 置为 0，再复制 `/sys/kernel/debug/tracing/trace`。

这组回答的是：ftrace 插桩本身是否足够轻。运行期间只有被测进程和内核 trace 写入，没有额外的 `cat` 进程、文件写入和导出 I/O。如果 C 组接近 baseline，说明正式实验可以使用 ftrace 作为内核态时间来源。

代价是 ring buffer 有容量上限。事件太密或 episode 太长时，旧事件可能被覆盖，最后复制出来的 `trace` 只剩较新的尾部。所以 C 组要么把 buffer 调大，要么控制 episode 长度。

### D 组：ftrace 实时导出

episode 开始前也要打开 tracepoint 和 `tracing_on`，但还要在 record 命令运行前启动一个后台导出进程，例如持续读取 `trace_pipe` 并写入 `raw/ftrace_D_RUN.log`。这个后台进程会在 episode 期间不断发生 `read()`、`write()`、调度和文件 I/O。

这组回答的是：实时导出是否把额外压力带进了实验。它比 C 组多出来的不是 ftrace 插桩，而是用户态导出链路。重点看 FPS、系统时间、RSS、上下文切换、日志大小和 lost events。若 D 组明显变差，后续正式实验应避免边跑边导出。

注意：如果 episode 跑完才开始读 `trace_pipe`，那就不是 D 组了；如果 ring buffer 已经覆盖，只会读到很短一段尾部数据。D 组正确顺序是“配置 tracepoint -> 清空 buffer -> 打开 `tracing_on` -> 启动实时导出 -> 启动 record -> record 结束 -> 停止导出 -> 关闭 `tracing_on`”。

### E 组：trace-cmd record

用 `trace-cmd record` 记录与 C/D 组相同的 tracepoint。

这组回答：`trace-cmd` 能不能替代手写 ftrace 导出流程。它通常更适合长时间采集，因为它围绕 per-CPU buffer 和 trace.dat 做了更完整的封装。

## 4. 建议 tracepoint

本实验不需要把所有内核细节都打开，只打开和主循环等待、摄像头、串口 I/O 直接相关的事件：

| tracepoint | 作用 |
|---|---|
| `syscalls:sys_enter_ioctl` / `syscalls:sys_exit_ioctl` | 观察摄像头 V4L2 ioctl 和串口 ioctl |
| `syscalls:sys_enter_pselect6` / `syscalls:sys_exit_pselect6` | 观察 OpenCV/V4L2 等待设备事件 |
| `syscalls:sys_enter_read` / `syscalls:sys_exit_read` | 观察串口和文件读取 |
| `syscalls:sys_enter_write` / `syscalls:sys_exit_write` | 观察串口写入 |
| `syscalls:sys_enter_clock_nanosleep` / `syscalls:sys_exit_clock_nanosleep` | 观察 `fps_sleep` / `busy_wait` 中可能进入内核的睡眠 |
| `syscalls:sys_enter_futex` / `syscalls:sys_exit_futex` | 观察 Python 线程事件、锁竞争和条件等待 |

如果事件量太大，优先保留 `ioctl`、`pselect6`、`clock_nanosleep` 和 `futex`。本实验的目标是校准工具开销，不是完整复原每一帧的调用链。

## 5. 内核自定义插桩

除了上节列出的标准 syscall tracepoint，本实验还使用了内核源码级 `trace_printk` 插桩。这些插桩在内核源码中通过 `ktime_get()` 手动计时，将结果以 `trace_printk` 写入 ftrace ring buffer，与标准 tracepoint 事件混合输出到同一个 `trace` 文件。相比标准 tracepoint 只记录进出时刻和参数，自定义插桩能提供更深层的语义信息。

### 5.1 插桩位置与输出格式

**pselect6 插桩**（`fs/select.c` → `do_select()` 函数）：

在 `do_select()` 入口记录 `pselect_start_time`，在 `poll_schedule_timeout()` 前后打点计算 `sleep_duration`，函数退出时通过 `trace_printk` 输出：

```
python-51217 [000] ..... 10070.805128: do_select:
  pselect6: total=30767298 ns, sleep=30759075 ns, context=8223 ns,
  ret=1, end_time=10070.614446893 s, fd=9, file=video2
```

| 字段 | 含义 |
|---|---|
| `total` | 本次 pselect6 从进入到返回的总墙钟耗时（ns） |
| `sleep` | 在 `poll_schedule_timeout()` 中实际阻塞睡眠的时间（ns） |
| `context` | 非睡眠的上下文处理时间 = total − sleep（ns） |
| `ret` | 返回值：就绪 fd 数，0 表示超时，−1 表示被信号中断 |
| `fd` | 就绪的文件描述符编号 |
| `file` | fd 对应的设备名（通过 `d_path()` 解析），如 `video0`、`video2` |

标准 `sys_enter_pselect6` / `sys_exit_pselect6` tracepoint 只记录 syscall 入口参数（`nfds`、`timeout`）和出口返回值，无法直接拆分睡眠时间和上下文处理时间，也不知道是哪个 fd 就绪。自定义插桩解决了这两个问题。

**futex 插桩**（`kernel/futex/syscalls.c` → `do_futex()` 函数）：

在 `do_futex()` 入口记录 `futex_start_time`，在 `futex_wait_multiple()` 前后打点计算 `sleep_duration`，函数退出时输出：

```
python-52739 [000] ..... 10257.007433: __arm64_sys_futex:
  futex: op=1, val=2147483647, ret=2, total=11722 ns, cpu=11722 ns, sleep=0 ns
```

| 字段 | 含义 |
|---|---|
| `op` | futex 操作码（0=WAIT, 1=WAKE, 9=WAIT_BITSET 等） |
| `val` | 用户传入的 `val` 参数 |
| `ret` | 返回值 |
| `total` | 本次 futex 调用总耗时（ns） |
| `cpu` | CPU 执行时间 = total − sleep（ns） |
| `sleep` | 在内核中实际阻塞睡眠的时间（ns） |

标准 `sys_enter_futex` / `sys_exit_futex` tracepoint 只记录 `uaddr`、`op`、`val` 参数和返回值，无法拆分 CPU 时间和睡眠时间。自定义插桩可以直接区分 futex 是快速解锁（sleep≈0）还是长时间等待（sleep 接近 total），从而判断 Python 线程间的锁竞争程度。

### 5.2 实测数据示例

C 组一次 episode 的 trace 文件（`ftrace_C_1.txt`，约 187 万条事件）中：

- 自定义 `do_select` 插桩事件：45,907 条，其中 Python 进程约占 1/3，能清晰看到摄像头等待周期（`fd=8, file=video0` 约 30 ms/次，`fd=9, file=video2` 约 30 ms/次）
- 自定义 `__arm64_sys_futex` 插桩事件：76,370 条，能区分 Python 主线程的 WAKE 操作（op=1, sleep=0）和子线程的 WAIT 操作（op=0, sleep 最大达 1.8 s）

### 5.3 为什么需要内核源码插桩而非 kprobe

理论上可以用 kprobe 动态钩住 `poll_schedule_timeout` 和 `futex_wait_multiple` 来实现类似拆分，但有两个限制：

1. **kprobe 只能钩入口和出口**，无法访问函数内部已经计算好的局部变量（如 `sleep_duration`）。要得到同样的拆分结果，需要在 kprobe 回调中重新做 `ktime_get()` 打点，逻辑比直接在源码中插入更复杂且不够准确。
2. **fd→文件名的解析**（`d_path()`）需要持有 `dentry` 引用和适当的锁上下文，kprobe 回调中调用 `d_path()` 有死锁风险，而 `do_select()` 原生上下文里调用是安全的。

代价是每次更换内核版本需要重新编译。本实验使用自编译内核，不构成额外负担。

## 6. 执行流程

### 6.1 记录环境快照

正式跑实验前，先按 `environment_snapshot_template.md` 填一份环境快照。至少记录：

- 操作系统版本、内核版本、Python 版本；
- LeRobot、PyTorch、torchvision、OpenCV、NumPy、pyserial、feetech-servo-sdk 版本；
- `/dev/video*`、`/dev/ttyACM*` 设备节点；
- 摄像头分辨率、像素格式、目标 fps；
- 树莓派温度、CPU 频率、供电状态；
- 模型权重路径、任务名、`chunk_size`、目标 `fps`。

### 6.2 每次 episode 的记录顺序

每个 run 都按同一个顺序记录：

1. 记录开始温度和 CPU 频率。
2. 启动对应组别的 tracing。
3. 用 `/usr/bin/time -v` 包住同一条 record 命令。
4. 停止 tracing。
5. record.py 自动采集 resource 指标、温度、频率，写入 `timing_stats.csv`。
6. 脚本打印 trace 文件大小和 lost events。

### 6.3 实验脚本

5 个独立脚本，各自处理一组实验。共享配置在 `_common.sh`。

```bash
cd ~/lerobot/analysis/04_tool_overhead

./run_A_baseline.sh            # A 组：无 tracing，5 次
./run_B_strace.sh              # B 组：strace 包裹，5 次
./run_C_ftrace_delayed.sh      # C 组：ftrace ring buffer，5 次
./run_D_ftrace_realtime.sh     # D 组：ftrace + trace_pipe 实时导出，5 次
./run_E_tracecmd.sh            # E 组：trace-cmd record，5 次

# 也可指定次数
./run_A_baseline.sh 3          # 只跑 3 次
```

**所有指标由 record.py 内部采集**（`resource` 模块 + sysfs 温度/频率），直接写入 `timing_stats.csv`，不再需要 `/usr/bin/time -v`。

**数据流**：

```
bash 脚本 ──设置 tracing──→ 调 record.py --timing-tag="A_1"
                                      ↓
                          record.py 内部采集：
                            record_loop → frames, obs_pct, inference_pct, ...
                            resource.getrusage() → user_time_s, system_time_s, max_rss_kb, ...
                            sysfs → cpu_temp, cpu_freq
                                      ↓
                          写入 timing_stats.csv（一行一个 episode）
```

**输出文件**：

| 文件 | 内容 |
|---|---|
| `analysis/timing_stats.csv` | record.py 自动写入，含 record_loop + resource + 温度全部指标 |
| `analysis/04_tool_overhead/raw/` | strace/ftrace/trace-cmd 的原始 trace 文件 |

### 6.4 注意事项

- C/D 组用 `syscalls:sys_enter_xxx`（有参数的 tracepoint），不用 `raw_syscalls/sys_enter`（只记录 syscall 号，无参数）；前者数据更丰富但每事件开销略高，更能体现真实条件
- C 组 `buffer_size_kb=32768` 对应每 CPU 32 MB；4 核 × 32 MB = 128 MB 总占用，40 s episode 约产生数十万事件，一般不会溢出；若 `grep "lost" raw/ftrace_C_*.txt` 有输出则需再调大
- D 组的 `sudo kill $pipe_pid` 依赖 `cat` 以 root 运行；若 `cat` 进程为另一个 sudo 子进程，改用 `sudo kill $(pgrep -f trace_pipe)` 替代

## 7. 数据表

所有指标由 record.py 写入 `analysis/timing_stats.csv`，一行代表一个 episode。

| 列名 | 含义 | 采集方式 |
|---|---|---|
| `timing_tag` | 分组标签（如 "A_1"、"C_3"） | bash 脚本传 `--timing-tag` |
| `model` | 模型名称 | record.py 自动提取 |
| `episode_idx` | episode 序号 | record.py 自动计数 |
| `frames` | 总帧数 | record_loop 累计 |
| `episode_total_s` | episode 墙钟时间 | record_loop 累计 |
| `fps_mean` | 平均 FPS | frames / episode_total_s |
| `obs_pct` / `inference_pct` / `action_pct` / `wait_pct` | 四阶段占比 | record_loop 累计 |
| `user_time_s` / `system_time_s` | 用户/系统 CPU 时间 | `resource.getrusage()` |
| `max_rss_kb` | 峾值 RSS | `resource.getrusage()` |
| `voluntary_cs` / `involuntary_cs` | 自愿/非自愿上下文切换 | `resource.getrusage()` |
| `cpu_temp_start_c` / `cpu_temp_end_c` | 开始/结束温度 | sysfs `thermal_zone0` |
| `cpu_freq_mean_mhz` | 平均 CPU 频率 | sysfs `cpufreq` |

`trace_file_mb` 和 `lost_events` 由 bash 脚本在终端打印，不在 CSV 中（需事后手动整理）。

## 8. 分析方法

以 A 组 baseline 为 100%，计算各组相对变化：

- `fps_drop_pct = (fps_A_mean - fps_group_mean) / fps_A_mean`
- `system_time_ratio = system_time_group / system_time_A`
- `rss_ratio = max_rss_group / max_rss_A`
- `phase_drift_pp = phase_pct_group - phase_pct_A`

画四张图即可支撑第 2 章：

1. 各组 FPS 相对 baseline 的下降比例。
2. 各组 `user_time_s` 和 `system_time_s` 对比。
3. 各组上下文切换次数对比。
4. 各组阶段占比漂移，重点看 `obs_pct` 和 `wait_pct` 有没有被 tracing 改变。

## 9. 验收标准

建议把正式采集方案定为 C 组或 E 组，前提是满足：

- 相对 baseline，`fps_mean` 下降不超过 5%；
- `obs_pct`、`inference_pct`、`action_pct`、`wait_pct` 任一漂移不超过 3 个百分点；
- `system_time_s` 没有接近 `strace` 组那种数量级放大；
- trace 日志无明显 lost events；
- 温度和 CPU 频率没有显示降频导致的系统性偏差。

如果 D 组变差，而 C/E 组正常，论文里就可以明确写：ftrace 插桩本身不是主要问题，实时导出才是额外开销来源；正式实验应采用 episode 后导出或 `trace-cmd record`。

## 10. 写回第 2 章的位置

实验完成后，第 2.5 节可以补一段实测结论：

> 在相同 episode 和相同 `record_loop` 参数下，`strace` 组系统时间明显上升，FPS 下降，因此只用于系统调用类型的定性确认；`ftrace` 延迟导出组与 baseline 接近，说明内核 ring buffer 插桩对主循环扰动较小；实时导出组的额外开销来自日志导出 I/O，因此本文正式阶段计时采用 ftrace 延迟导出或 `trace-cmd record`。
>
> 此外，本文在内核源码中对 `pselect6`（`fs/select.c`）和 `futex`（`kernel/futex/syscalls.c`）插入了 `trace_printk` 计时桩，通过 `ktime_get()` 手动打点，将每次调用的总耗时拆分为睡眠时间和上下文处理时间。对于 `pselect6`，额外通过 `d_path()` 将就绪 fd 解析为设备名（如 `video0`、`video2`），从而在 trace 日志中直接识别出摄像头帧等待和串口等待。标准 syscall tracepoint 只记录进出时刻和参数，无法提供这种拆分和语义解析。

第 2.6 节则引用环境快照，说明所有实验的硬件、软件包版本、摄像头参数和 CPU 热状态都被记录。
